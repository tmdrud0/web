대회 스코어보드를 Redis에 두면 조회 성능은 아주 좋아진다. 문제는 장애 이후다.

Redis가 예전 스냅샷으로 복구되면, DB에는 이미 반영 근거가 남아 있는데 Redis 쪽 상태만 과거로 돌아갈 수 있다. 이 순간부터 운영자가 진짜로 풀어야 하는 문제는 Redis를 다시 띄우는 것이 아니라, 무엇이 유실됐는지 어떻게 다시 찾아 반영할 것인가다.

이번 글은 그 복구 경로를 어떻게 설계했는지 정리한 내용이다.

## 문제: `outbox.id`만으로는 부족했다

처음 떠올리기 쉬운 방법은 `contest_submission_outbox.id`를 기준으로 복구하는 방식이다.

하지만 이 방식은 몇 가지 아쉬움이 있었다.

- `outbox.id`는 DB insert 순서이지 Redis 적용 순서가 아니다.
- 실패와 재시도 때문에 일부 id는 비어 있을 수 있다.
- Redis가 예전 스냅샷으로 복구돼도 `outbox.id` 자체는 되돌아가지 않는다.

즉 DB 기준으로는 단순하지만, Redis 관점에서는 어디까지 반영됐는지를 자연스럽게 알기 어렵다.

## 선택: 복구 감지용 `redis_seq`를 분리했다

최종적으로는 역할을 분리했다.

- `outbox.id`
  - 멱등 적용 키
- `redis_seq`
  - 복구 감지 키

`redis_seq`는 Redis가 `contestSubmissionId` 기준으로 발급한다.

- 이미 본 제출이면 기존 seq를 반환
- 처음 보는 제출이면 새 seq를 발급

그리고 이 값을 outbox에도 함께 저장했다.

이 설계의 핵심은 Redis가 예전 스냅샷으로 복구될 때 드러난다.

- Redis의 seq counter도 과거로 돌아간다.
- `contestSubmissionId -> redis_seq` 매핑도 과거 상태가 된다.
- 그 뒤 새 결과가 들어오면 예전에 쓰였던 `redis_seq`가 다시 발급될 수 있다.

이때 Spring batch 서버는 outbox에서 중복된 `redis_seq`를 복구 신호로 감지하고 replay를 시작할 수 있다.

즉 복구를 별도의 강한 제어 흐름으로만 두지 않고, 평소 처리 흐름 안에 녹여 넣은 셈이다.

## 고려했던 대안들

설계 과정에서 세 가지 복구 방식을 비교했다.

### 1. DB가 gapless seq를 직접 발급하는 방식

이 방식은 Redis 바깥, 즉 DB가 복구 기준이 되는 seq를 직접 관리한다.

장점:

- seq가 DB에 영속되므로 Redis snapshot rollback과 무관하다
- 새 트래픽이 없어도 복구를 진행할 수 있다

단점:

- gapless를 유지하려면 seq 발급 구간이 직렬화되기 쉽다
- 여러 서버에서 부담 없이 확장하기가 까다롭다

### 2. 명시적 복구 모드

Redis의 현재 max seq나 체크포인트를 읽고, 그보다 큰 outbox를 다시 밀어 넣는 방식이다.

장점:

- 복구 범위가 명확하다
- 새 이벤트가 없어도 바로 복구 가능하다

단점:

- 별도 복구 절차가 필요하다
- 장애 감지와 시작 시점을 운영에서 관리해야 한다

### 3. 자연 복구

평소처럼 outbox를 계속 처리하다가, Redis가 과거 스냅샷으로 돌아온 뒤 duplicate `redis_seq`가 나오면 replay하는 방식이다.

장점:

- 별도 복구 모드가 필요 없다
- 운영 흐름을 끊지 않는다

단점:

- 복구 속도가 새 이벤트 유입량에 영향을 받는다
- 트래픽이 적으면 회복이 늦어진다

## 최종 구조

최종적으로는 두 가지를 같이 썼다.

### 평소 운영 중

- outbox를 계속 소비한다
- duplicate `redis_seq`를 주기적으로 찾는다
- 중복 seq가 보이면 필요한 구간을 replay한다

즉 운영 중에는 절차를 단순하게 두고, 장애가 나더라도 흐름을 크게 바꾸지 않는다.

### 대회 종료 시점

- Redis의 `max seq`를 기준으로 catch-up replay를 한 번 더 수행한다

이 단계는 자연 복구만으로 남을 수 있는 틈을 마무리하는 역할이다. 평소에는 간결하게 운영하고, 중요한 종료 시점에는 정합성을 한 번 더 확인하는 방식이다.

## 역할 분리

구성은 아래처럼 나눴다.

- judge 서버
  - `contest_submission_result`, `contest_submission_outbox` 저장
- batch 서버
  - outbox를 Redis scoreboard에 반영
  - duplicate `redis_seq` replay
  - 종료 시 catch-up replay
- Redis scoreboard
  - 빠른 조회용 파생 상태
  - `outbox.id` 기준 멱등 적용

이 구조의 장점은 빠른 조회와 복구 책임이 섞이지 않는다는 점이다. Redis는 조회를 빠르게 하는 데 집중하고, 정합성 회복의 로직은 batch 서버 쪽에서 흡수한다.

## 배운 점

이 작업을 하면서 느낀 건 캐시 복구 문제는 결국 무엇을 저장할까보다 무엇을 신호로 삼을까의 문제에 가깝다는 점이었다.

`outbox.id`는 멱등성에는 잘 맞았지만, 복구 감지에는 맞지 않았다. 반대로 `redis_seq`는 적용 순서를 설명하고 복구를 감지하는 데 더 적합했다. 역할을 나누자 설계가 훨씬 명확해졌다.

또 하나는 복구를 운영 절차로만 두면 결국 사람이 개입할 지점이 늘어난다는 점이었다. 가능한 한 평소 흐름 안에서 자연스럽게 회복되도록 만드는 편이 실제 운영에서는 훨씬 다루기 쉬웠다.

## 마무리

Redis 스코어보드는 조회를 빠르게 만들어 주지만, 그만큼 원본이 아닌 상태를 운영하게 만든다. 그래서 성능 최적화만큼이나 중요한 게 복구 설계였다.

이번 구조에서는 `outbox.id`와 `redis_seq`의 역할을 분리해서,

- 평소에는 자연 복구로 단순하게 운영하고
- 중요한 시점에는 catch-up replay로 정합성을 보완하는

두 겹의 안전장치를 두었다.

빠른 시스템은 만드는 것만큼, 틀어졌을 때 어떻게 되돌릴지도 같이 설계해야 오래 버틴다는 걸 다시 확인한 작업이었다.
