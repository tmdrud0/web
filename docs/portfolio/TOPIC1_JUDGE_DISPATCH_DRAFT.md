**주제 1 · 채점 작업 분배 — 첫 판단과 그 검증**

# 채점 서버가 죽으면, 처리 중이던 제출은 누가 책임지나?

제출 원본은 MySQL에 안전하게 남는다. 문제는 그다음이다. 채점 서버가 가져간 작업은 그 서버와 함께
주인을 잃는다. 제출은 "채점 중"인 채로 남고, 참가자는 결과를 받지 못한다.
풀어야 할 것은 데이터 유실이 아니라 **진행 중인 작업의 소유권**이었다.

### 첫 번째 해결 — 새 인프라 없이 MySQL로

제출이 이미 DB에 있으니, 작업 상태도 같은 곳에 두면 운영할 구성요소가 늘지 않는다.
소유권 문제를 세 가지로 나눠 각각 막았다.

| 막아야 할 일 | 방법 |
|---|---|
| 두 서버가 같은 제출을 동시에 가져간다 | `SELECT … FOR UPDATE SKIP LOCKED` — 다른 서버가 잠근 행은 기다리지 않고 건너뛴다 |
| 가져간 서버가 죽어 작업이 방치된다 | 가져간 시각을 기록하고, 일정 시간(lease)이 지나면 다음 claim이 다시 가져간다 |
| 늦게 깨어난 원래 서버가 결과를 덮어쓴다 | 가져갈 때마다 새 토큰을 발급하고, 완료 시 토큰이 일치할 때만 기록한다 |

`대기 → (토큰 발급) 채점 중 → (토큰 확인) 완료` · lease가 지나면 `채점 중 → 다시 가져감`

### 남은 선택 — lease를 얼마로 잡을까

- **짧으면** 오래 걸리는 정상 채점을 죽은 것으로 보고 중복 실행한다.
- **길면** 진짜 장애에서 회수가 늦다.

고를 근거가 없었다. 여기서 나는 이 트레이드오프를 **이론으로만 보고** 작업 소유를 브로커(RabbitMQ)의
ACK로 옮기기로 했다. 측정은 옮긴 뒤에, 두 방식을 모두 남겨 두고 했다.

### 측정해 보니 — 트레이드오프는 실재했다

포화 근처(110 RPS, 노드당 in-flight 16, worker 16, 채점 95% 50ms / 5% 2초, 각 1회)

| 지표 | lease 2.5초 | lease 1초 | 읽는 법 |
|---|---:|---:|---|
| 실제 중복 채점 | 0건 | 354건 | 전체의 4.9%, 전부 2초짜리 작업 |
| 계산상 worker 비용 | 기준 | +67.7% | 5%만 중복됐는데 긴 작업이라 비용은 2/3 늘었다 |
| 중복 안 된 50ms 작업 p95 | 715ms | 16,358ms | 중복이 worker를 점유해 멀쩡한 작업까지 밀렸다 |
| 유실 · 최종 불일치 | 0 / 0 | 0 / 0 | 정합성은 지켜졌다 — 비용과 지연의 문제였다 |

그리고 안전한 값은 고를 수 있었다. in-flight 64 · 100 RPS에서 2초는 중복 163건을 만들었지만
4초와 10초는 모두 0건, 처리량도 같았다.
돌이켜 보면 heartbeat로 "오래 걸리는 작업"과 "죽은 서버"를 구분할 수도 있었지만, 4초에서 이미
중복이 없어 소유 목록 관리·멈춘 작업의 상한 같은 복잡도를 더할 이유가 없었다.

### 그런데 — lease가 사용자 지연을 좌우하지 않았다

채점 서버 한 대를 강제 종료(SIGKILL)해 봤다.

| 장애 중 짧은 작업 p95 | lease 4초 | lease 10초 |
|---|---:|---:|
| 50 RPS (남은 한 대가 감당 가능) | 0.88s | 0.44s |
| 100 RPS (남은 한 대의 용량 초과) | 10.5s | 10.1s |

lease가 바꾼 것은 죽는 순간 잡혀 있던 **수십 건**의 회수 시점뿐이었다.
전체 지연은 **남은 서버가 들어오는 제출을 감당하느냐**로 갈렸다.

> **트레이드오프는 실재했지만, 사용자 경험을 좌우하는 요인이 아니었다.**
> 이론만 보고 내린 결정이었다. 그러면 브로커를 계속 둘 이유가 있는가 — 다시 물어야 했다.

**주제 1 · 채점 작업 분배 — 문제를 다시 정의하고 검증하다**

# 회복 속도가 아니라 용량이 문제라면, 그 비용은 누가 치르는가

### 다시 정의한 문제

대회 부하는 평탄하지 않다. 평시 위에 몇 분짜리 **5배 피크**가 얹히고, 그 안에 짧은 **10배 피크**가 있다고
봤다. 10배 구간의 대기는 허용하더라도, 5배 구간에서 대기열이 쌓이지 않으려면 5배를 처리할 용량이 필요하다.
그렇게 용량을 잡으면 평시에는 한 대가 죽어도 여유가 충분하고, 피크에는 참가자가 이미 수십 초 대기를
겪는다. 어느 쪽에서도 회복 속도는 체감 요인이 아니다.

그래서 브로커의 가치를 **"같은 피크 경험을 더 적은 자원으로 주는가"**로 다시 세웠다.

- **부하 모양**: 평시 1배 → 5배 → 10배 → 5배 → 평시 (5배 구간 2분 30초, 그 안의 10배 30초. 실험 시간 때문에 절반으로 축소)
- **변수**: 채점 worker 수로 정한 용량 = 평시 부하의 5.4 / 6.8 / 8.1배
- **지표**: p99 대신 **대기열이 남아 있는 시간**. p99는 대회가 길수록 평시 제출에 희석되어 피크를 가린다.
- **규칙**: 반복 실행, 거절된 제출이 통계에서 빠지지 않도록 503이 1건이라도 나온 실행은 버린다.

### 기대와 결과

| 브로커에 기대한 것 | 결과 | 근거 |
|---|---|---|
| 장애 때 더 빨리 회복 | **아니었다** | 피크 중 채점 서버를 죽여도 두 방식 모두 대기열 170초. 재전달 지연을 0·4·30초로 바꿔 넣어도 같았다 |
| 채점 서버가 덜 논다 | **조금** | 실제 용량이 명목 대비 MySQL 77~80%, 브로커 79~84% — 차이 3~5%p |
| DB 경합이 준다 | **예상보다 컸다** | 아래 |

의심한 것: MySQL을 덜 튜닝했나(poll 간격 100→20ms: 처리량 그대로, DB CPU만 +34~44%),
가짜 채점이라 그런가(실제 CPU 연산으로 바꿔도 같은 결론). 어느 쪽도 결론을 바꾸지 않았다.

### 차이는 DB에서 났다

처리량을 14배로 키우자(평시 70 RPS, 같은 용량 배수) 채점 효율은 여전히 비슷했다. 그런데 DB가 달랐다.

| 최고 피크 30초, DB CPU 한도 2코어 | MySQL 방식 | 브로커 방식 |
|---|---:|---:|
| 평균 DB CPU | 1.6~1.7코어 | 약 1.2코어 |
| CPU 한도에 막힌 시간 | 23~28초 | 4~6초 |
| 피크 뒤 평시 120초 중 막힌 시간 | 18~84초 | 0초 |

MySQL 방식의 DB 부하는 유입이 아니라 채점 속도를 따라간다. 피크가 끝나도 대기열을 비우는 동안
claim과 완료 처리가 DB를 계속 두드린다. 그리고 이 DB는 **유실되면 안 되는 제출 원본도 저장한다.**
이 차이는 비용이 아니라 위험이다.

---

**기대는 채점 서버였지만, 브로커가 아낀 건 DB였다.**
장애 지연도, 채점 처리량도 크게 달라지지 않았다. 달라진 것은 피크에 제출 저장과 같은 DB가 남기는
여유였다. 어느 방식이든 필요한 채점 서버는 명목이 아니라 실측 용량(이번 조건에서 명목의 약 67~84%, 규모가 클수록 낮았다)으로 계산해야 하고,
이 값 하나로 대기열 길이가 재현됨을 모델로 확인했다.

**다시 설계한다면**
지금 규모에서는 MySQL 방식도 충분히 유효하다 — 채점 효율 차이는 3~5%p이고 운영할 인프라가 하나 적다.
브로커를 유지하는 이유는 채점 효율이 아니라 DB 여유이고, 처리량이 커져 DB 여유가 제출 저장을 위협할 때
의미가 커진다. 그 판단을 확인하려고 피크 중 DB CPU 여유를 지켜볼 지표로 둔다.
