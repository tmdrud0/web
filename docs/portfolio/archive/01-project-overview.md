## 1.1 무엇을 만들었나

문제를 풀고 코드를 제출하면 채점 결과와 순위를 돌려주는 온라인 저지 API 서버입니다.
일반 제출도 지원하지만, 이 포트폴리오가 다루는 범위는 **대회(contest) 제출 경로**입니다.

대회 제출은 일반 제출과 부하 특성이 다릅니다.

- 정해진 시간에 수천 명이 동시에 제출합니다.
- 제출이 유실되면 참가자가 대회 중에 알 수 없습니다.
- 순위가 실시간으로 보여야 하지만, 그 순위가 대회 종료 후 최종 순위와 **달라지면 안 됩니다**.

이 세 조건을 동시에 만족시키는 것이 프로젝트의 실제 문제였습니다.

## 1.2 왜 이 구조로 만들었나

**개인 프로젝트인데 인스턴스를 5개로 나눈 이유를 먼저 밝힙니다.**
사용자 수 때문이 아니라, 다음을 직접 겪어보기 위한 의도된 구성입니다.

- 프로세스가 죽었을 때 어디까지 복구되는지 **말할 수 있는 시스템**을 만들어보기
- 단일 JVM 안에서는 드러나지 않는 문제(메시지 중복 전달, 이벤트 순서 역전, 인스턴스별 ID 충돌)를 실제로 만나보기
- 병목을 특정 서비스에 귀속시킬 수 있도록 자원 상한을 고정해놓고 측정하기

따라서 이 프로젝트의 성과는 처리량 수치가 아니라 **"어떤 장애를 어떻게 흡수하는지 설명할 수 있게 된 것"**입니다.

## 1.3 시스템 구성

![시스템 아키텍처](diagrams/architecture.svg)

| 역할 | 인스턴스 | Spring profile | 주 책임 |
|---|---|---|---|
| **Web** | `web-1`, `web-2` | `multi-web` | JSON API, 제출 검증, 제출 원본과 judge outbox 저장 |
| **Batch** | `batch-1` | `multi-batch` | judge outbox relay, 스코어보드 stream 소비, 랭킹 배치 |
| **Judge** | `judge-1`, `judge-2` | `multi-judge` | 채점 큐 소비, 채점, 결과 저장, result stream 발행 |
| **Data** | MySQL, Redis, RabbitMQ | — | 원본 / 파생 상태 / durable 전달 |
| **Edge** | Nginx | — | 두 Web 인스턴스 로드밸런싱 |

### 저장소별 역할을 명확히 나눴습니다

| 저장소 | 역할 | 유실됐을 때 |
|---|---|---|
| **MySQL** | 제출 원본, 중복 여부의 **최종 권위** | 복구 불가 — 절대 유실되면 안 되는 유일한 상태 |
| **Redis** | 스코어보드 **파생 상태** | MySQL 결과에서 언제든 재구성 가능해야 함 |
| **RabbitMQ** | 작업 **전달** 수단 (원본 저장소 아님) | 재전달 또는 outbox에서 재발행 |

이 구분이 프로젝트 전체 설계의 기준선입니다.
"Redis 스코어보드는 파생 상태다"라는 원칙 하나가
[3장](03-scoreboard-delivery.md)의 복구 설계 전체를 결정했습니다.

## 1.4 측정 환경

절대 수치가 아니라 **같은 전제에서의 상대 비교**를 위해 자원 상한을 고정했습니다.

| 항목 | 값 |
|---|---|
| 호스트 | AMD Ryzen 5 5600 (6C/12T), 16GB RAM, Windows 11 |
| 실행 | Docker Desktop (WSL2), 12 vCPU / 14GB 예산 |
| 애플리케이션 상한 합 | 7.5 CPU / 9,344M (9개 컨테이너) |
| 관측 스택 상한 합 | 2.2 CPU / 2,112M (7개 컨테이너) |
| 부하 생성 | Gatling 3.10.5 (Windows 호스트에서 별도 실행) |

> 부하 생성기와 서버가 같은 물리 머신에 있으므로 **절대 처리량은 용량 수치로 인용하지 않습니다.**
> 모든 비교는 같은 상한, 같은 시나리오, 같은 커밋 조건에서 수행했습니다.
