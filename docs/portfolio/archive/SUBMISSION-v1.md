# 신승경 · 백엔드

> `✂` 로 시작하는 줄은 편집 메모다. 제출 전에 지운다.

장애가 났을 때 **어디까지 복구되는지 말할 수 있는 시스템**을 만드는 데 관심이 있다.
온라인 저지를 혼자 만들면서, 대회 중 제출이 몰릴 때 데이터가 유실되거나
실시간 순위가 최종 순위와 어긋나는 문제를 주제로 삼았다.

단일 JVM에서는 재현되지 않는 문제 — 메시지 중복 전달, 이벤트 순서 역전, 인스턴스별 ID 충돌 —
를 다루기 위해 분산 구성을 전제로 설계했다.

## 핵심 역량

**정합성을 순서와 중복에 의존하지 않게 설계한다.**
채점 완료 순서는 제출 순서와 다르다. 누적 방식 스코어보드는 이것 때문에 대회 중 참가자가 본
순위와 최종 순위를 다르게 만들었다. 누적을 버리고 매번 재계산하도록 바꿨다. → 3장

**측정 조건을 의심한다.**
`prefetch`를 올렸을 때의 꼬리 악화는 포화 상태에서 재면 +25%로 보이고, 포화를 걷어내면
+334%다. 백로그라는 지배항이 분자와 분모를 함께 키워 효과를 희석하기 때문이다.
무엇을 재는지보다 **어떤 조건에서 재는지**가 결론을 바꾼다. → 2장

**근거로 쓸 수 있는 수치와 없는 수치를 구분한다.**
부하 발생기와 서버가 같은 호스트를 나눠 쓰므로 절대 처리량은 용량 수치로 쓰지 않는다.
모든 비교는 같은 환경의 짝실험으로 설계했고, 순서를 뒤집어 재현해 워밍업 교란을 배제했다.

# 1. 온라인 저지 (개인 프로젝트, 2025.09 ~ 2026.08 · 11개월)

문제를 풀고 코드를 제출하면 채점 결과와 순위를 돌려주는 API 서버다.
일반 제출도 있지만 이 문서가 다루는 범위는 **대회 제출 경로**다. 정해진 시간에 제출이 몰리고,
유실되면 참가자가 대회 중에 알 수 없으며, 실시간 순위가 최종 순위와 달라지면 안 된다.
Codeforces를 쓰면서 겪은 것들이 그대로 요구사항이 됐다.

| 분류 | 기술 |
|---|---|
| 언어·프레임워크 | Java 17, Spring Boot 3.4 |
| 저장소 | MySQL 8.0, Redis 7 |
| 메시징 | RabbitMQ 4.1 — quorum queue, stream queue, publisher confirm, DLQ |
| 데이터 접근 | Spring Data JPA, JDBC Template, Flyway |
| 인프라 | Docker Compose, Nginx |
| 측정 | Gatling, Prometheus, Grafana, JFR |

```
[그림 1] 시스템 아키텍처

  Client → Nginx → Web ×2 → MySQL(제출 원본 + judge outbox, 같은 트랜잭션)
  → Batch relay → RabbitMQ quorum queue → Judge ×2 → MySQL(채점 결과)
  → RabbitMQ result stream → Batch consumer → Redis Lua(스코어보드 + offset) → MySQL(적용 시각)

  MySQL 파랑 / Redis 빨강 / RabbitMQ 보라 / 애플리케이션 회색. 이후 모든 그림에서 같은 색을 쓴다.
```

저장소마다 역할을 하나씩만 준다.

- **MySQL** — 제출 원본과 중복 여부의 최종 권위. 유일하게 유실되면 안 되는 상태다.
- **Redis** — 스코어보드 파생 상태. MySQL 결과에서 언제든 같은 값으로 재구성할 수 있어야 한다.
- **RabbitMQ** — 작업 전달 수단. 원본 저장소가 아니다.

이 세 줄이 아래 두 장의 판단 기준 전부다.

### 측정 전제

수치를 싣기 전에 그 수치가 설명하지 않는 것을 먼저 적는다.

- **단일 호스트다.** web·judge·MySQL·RabbitMQ·Redis가 Docker 예산 하나를 나눠 쓰고,
  Gatling은 같은 호스트의 코어를 두고 그 VM과 경쟁한다.
- **채점이 `Thread.sleep`이다.** 블로킹 호출의 대용으로는 타당하지만 커넥션 풀 한계·타임아웃·
  부분 실패를 모델링하지 않는다.
- **닫힌 부하 모델이다.** 가상 사용자가 직전 응답을 기다리므로 서버가 느려지면 부하가 저절로 줄고,
  실제 장애 때의 재시도 증폭을 재현하지 못한다.
- **네트워크 지연이 0이다.** 전부 loopback이다.

따라서 아래 수치는 *절대 성능*이 아니라 **구조가 어디서 막히는가**의 증거로 읽어야 한다.

# 2. 대회 제출 파이프라인

**채점 작업 분배를 DB claim에서 RabbitMQ work queue로 옮겼다.**
DB claim 구조도 동작했다. 문제는 timeout·heartbeat·lease·sweeper를 직접 만들고 그 값을 정할
근거까지 스스로 마련해야 했다는 것이다. timeout이 짧으면 정상적으로 오래 걸린 작업을 중복
채점하고 길면 장애 복구가 늦어지는데, 그 사이를 고를 기준이 없었다.
재전달과 in-flight 제한은 broker가 이미 검증한 기능이다.

지켜야 할 조건은 네 개였다. ① HTTP 성공을 반환했다면 제출 원본은 DB에 commit되어 있다
② `(contest, problem, user, codeHash)`가 같은 제출은 한 건만 저장한다
③ 채점이 늦어져도 다른 제출이 같이 막히지 않는다
④ 프로세스나 broker 장애 후 미완료 작업을 다시 처리할 수 있다.

부하 모델은 최대 1,000 TPS, 채점 평균 10ms, **1,000건 중 1건이 최대 2초**로 잡았다.
평균만 보면 어떤 구조든 통과한다. ③번과 마지막 가정이 구조를 갈랐다.

```
[그림 2] 채점 구조의 변화 — 각 단계 아래 한계를 ✕ 한 줄로 붙인다

 V0   HTTP 저장 → Spring event → async listener → 채점 API
      ✕ 이벤트가 JVM 메모리에만 있다. commit 후 listener 전에 죽으면 영원히 채점되지 않는다
 V2   SKIP LOCKED claim → 긴 트랜잭션 안에서 병렬 채점 → 결과 commit
      ✕ 99건이 10ms에 끝나도 1건이 2초면 트랜잭션 전체가 2초 (head-of-line blocking)
 V3   짧은 claim → 메모리 큐 + worker → 결과 batch 저장 → sweeper가 오래된 claim 회수
      ✕ 격리는 됐지만 timeout·heartbeat·lease를 직접 만들고 그 값을 정할 근거가 없다
 현재  judge outbox(제출과 같은 트랜잭션) → quorum queue(prefetch=1) → Judge ×2 → 결과 commit
      ✓ 재전달 · in-flight 제한 · retry · DLQ를 broker가 담당

 V0~V3는 회색, 현재만 초록. DB가 작업 상태를 쥐던 구조에서 broker가 쥐는 구조로
 넘어가는 지점이 보여야 한다.
```

## 무엇을 얻고 무엇을 지불했나

**얻은 것.** claim 상태 관리 코드가 통째로 사라졌다. `prefetch`로 consumer별 in-flight를
제한하고, retry 소진 메시지는 DLQ로 보낸다.

**Kafka가 아닌 이유.** classic consumer는 `poll()`로 받은 record를 worker pool에 넘기는 순간
완료 순서가 offset 순서와 어긋난다. offset 10이 느리고 11~20이 먼저 끝나도 20까지 commit할 수
없으니 완료 구간을 직접 추적해야 한다 — DB claim에서 벗어나려다 형태만 다른 같은 복잡성을 다시
만드는 셈이다. 아래 `prefetch` 실험이 이 판단을 한 번 더 확인시켜 줬다.
**`prefetch`는 1로 되돌릴 수 있지만 파티션은 그럴 수 없다.** 파티션이 곧 큐이고 순서 보장이
head-of-line blocking과 같은 것이라, 튜닝으로 제거할 수 없는 구조적 성질이 된다.
거기에 `max.poll.interval.ms` 초과 리밸런스로 인한 중복 처리라는, RabbitMQ에 없는 실패 모드가
붙는다. 꼬리가 두꺼울수록 위험이 커지는데 이 워크로드가 정확히 그렇다.

**지불한 것.** DB와 broker 사이에 2PC가 없으므로 at-least-once다. relay는 confirm을 받으면
outbox를 `PUBLISHED`로 바꾸고 그 이후는 추적하지 않으므로, outbox가 있다고 broker durability를
낮출 수도 없다 — quorum queue와 persistent message를 그대로 유지해야 한다.
대신 제출 원본과 `contest_judge_outbox`를 같은 트랜잭션에 commit해서
**중복 여부의 권위만은 broker가 아니라 DB에** 남겼다. 중복 전달은 채점 결과 PK와 `INSERT IGNORE`,
그리고 결과가 이미 있으면 채점 API를 호출하지 않고 넘어가는 재전달 경로로 흡수한다.

## "최대 처리량"은 하나가 아니다

제출은 세 단계를 지나고, 각 단계가 앞 단계보다 느려서 경계마다 큐가 하나씩 생긴다.
단일 숫자로 최대 처리량을 말하면 어느 쪽이든 오해가 된다.

| 단계 | 하는 일 | 상한 |
|---|---|---:|
| 유입 | HTTP 접수 → 중복 해시 → bulk INSERT commit | **1,014 /s** |
| relay | judge outbox claim → RabbitMQ 발행 | **640 /s** |
| 채점 | consumer 32개 → 결과 commit → ACK | **150 /s** |

유입이 채점의 **6.8배**다. 이 격차를 durable outbox가 흡수하는 것이 설계 의도였고 실제로 그랬다.
접수는 commit 이후에만 `202`를 반환하므로 "접수했다고 답한 뒤 잃는" 경로는 없다.

쓰기 경로는 오히려 부하에서 효율이 올라간다. 제출 1,000/s에서 bulk writer의 평균 청크가
`3.5 → 22.7`건, 활성 워커가 `1 → 4`로 올라가며 삽입 속도가 `226 → 1,092.9 행/s`가 됐다.
한가할 때는 건당 처리에 가깝고 밀리기 시작하면 배치가 뭉쳐 건당 비용이 떨어진다.
저부하 수치로 선형 외삽하면 이 자기조절을 놓친다.

### 병목은 채점이고, 그것은 CPU가 아니다

| judge 노드 자원 | 실측 | 한도 | 여유 |
|---|---:|---:|---:|
| CPU (정상 상태) | 0.06 core | 0.75 | 12배 |
| 메모리 | 439–525 MB | 768 MB | 1.5배 |
| **리스너 스레드** | **16 × 2 노드** | **16 × 2** | **없음** |

처음에는 judge CPU가 72~78%로 관측돼 CPU 한도가 처리량을 깎는다고 판단했다. 컨테이너를
recreate한 런과 웜 상태 런의 CPU 시계열을 비교하니 `74% → 100초에 걸쳐 7%`로 감쇠하는 JIT 컴파일
곡선이었고, 샘플러의 "피크 CPU"가 그 초반 스파이크를 집고 있었다. 웜 상태의 정상 CPU는 7~9%다.

스레드 하나가 메시지 하나에 묶이는 시간은 `32 ÷ 150 = 213ms`다. 이 중 채점 sleep이 147.5ms이고,
**나머지 65ms는 결과 배치 쓰기·outbox insert·ACK 왕복 같은 블로킹 I/O**다. CPU가 아니라 대기라서
CPU 여유가 남는다. concurrency를 64에서 16으로 줄인 근거 주석은 같은 조건에서 217/s를 계산하는데
실측은 150/s다 — sleep만 세고 메시지당 65ms를 빼먹은 계산이었다.

## `prefetch`: 여유가 있을 때 꼬리가 증폭된다

`prefetch`를 1 / 4 / 64로 바꿔 짝실험했다. 도착률·서비스 분포·consumer 수는 전부 고정하고
디스패치 정책만 바꿨다. 부하는 139/s, 용량의 79%라 지속 백로그가 없다.

| prefetch | p50 | p95 | p99 | max | consumer당 대기 |
|---:|---:|---:|---:|---:|---:|
| 1 | 0.322s | 2.119s | **2.376s** | 2.844s | 0 |
| 4 | 0.312s | 2.258s | **3.975s** | 6.101s | 1.18 |
| 64 | 1.297s | 6.433s | **10.308s** | 16.706s | 6.37 |

**`prefetch=4`에서 이미 p99가 67% 나빠지는데 p50과 p95는 그대로다.** 대시보드에서 흔히 보는 두
지표가 멀쩡하니 공짜처럼 보이는 것이 가장 위험한 지점이다.

broker는 "이 consumer에게 밀어넣을 자리가 있나"를 보고 메시지를 배정한다. 스레드가 한가한지를
보는 것이 아니다. `prefetch=1`일 때만 이 둘이 같은 말이 된다. 그보다 크면 배정 결정에 가용성
정보가 실리지 않고, 한번 로컬 버퍼에 들어간 메시지는 **옆 consumer가 놀고 있어도 회수되지 않는다.**
work-conserving 큐 하나가 head-of-line blocking을 가진 32개의 독립 FIFO로 쪼개진다.

실측 대기 건수로 회귀하면 `p99 ≈ 2.4s + 1.3s × 대기건수`이고, 이 식이 `prefetch=4`에 3.93초
(실측 3.98), `prefetch=64`에 10.68초(실측 10.31)를 준다. 상한이 16배 차이인데 결과가 2.6배인
이유는 **상한이 아니라 실현 점유가 손해를 결정**하기 때문이다. 64에서도 버퍼는 상한의 11%만 찼다.

> **측정 조건이 결론을 바꿨다.** 같은 변경을 포화 상태(도착 > 용량)에서 재면 p99 악화가 +25%로
> 보인다. 포화를 걷어내면 +334%다. 백로그라는 지배항이 분자와 분모를 동시에 키워 효과를 희석하기
> 때문이다. 순서를 뒤집어 재현했을 때 p99가 `2.372 → 2.376s`, `10.458 → 10.308s`로 일치해
> 워밍업 교란도 배제했다.

## 백로그는 병목 바로 앞에만 앉는다

제출 1,000/s를 150초 넣었다. 127,687건이 접수됐고 전부 처리됐다. 피크 시점에 큐를 합치면
약 **132,000건** — 접수한 거의 전부가 동시에 줄을 서 있었다.

| 버퍼 | 위치 | 영속 | 피크 | 거동 |
|---|---|:-:|---:|---|
| 제출 in-flight | web JVM | ✕ | 410 / 800 | 여유 |
| judge outbox | MySQL | ✓ | 37,842 | 부하 종료 87초 만에 해소 |
| **RabbitMQ ready** | 브로커 | ✓ | **94,211** | 이후 9분에 걸쳐 배수 |
| scoreboard 반영 대기 | MySQL | ✓ | 67 | 병목 하류라 굶음 |

judge outbox는 유입(1,014)과 relay(640)의 차이만큼만 쌓이므로 부하가 멈추면 곧 따라잡는다.
RabbitMQ는 relay(640)와 채점(150)의 격차가 4배라 나머지 9분을 여기서 쓴다.
총 배수 **10.4분, 유실 0**.

하류 큐가 얕은 것은 건강 신호가 아니다. scoreboard 반영 대기는 모든 런에서 50~70을 유지했는데,
채점이 끝나야 행이 생기므로 상류가 막히면 유입 자체가 제한되기 때문이다. 조건이 나쁜 런에서
오히려 더 얕아졌다. **얕은 큐 = 정상이 아니라, 얕은 큐 = 상류 확인 필요.**

```
[그림 3] 단계별 상한과 백로그 위치

  Client ─(1,014/s)→ Web ─┬─ 제출 in-flight  410/800  (비영속)
                          │
  ═══════════════ 영속성 경계 : DB commit ═══════════════
                          │
              judge outbox 37,842 ─(640/s)→ RabbitMQ ready 94,211 ─(150/s)→ Judge ×2
                                                                              │
                                                          scoreboard 반영 대기 67

  경계 위는 주황 점선(유실 가능), 아래는 실선. 화살표에 각 단계 상한을 달고,
  버퍼 상자에 피크값을 적는다. 상한이 꺾이는 지점 바로 앞이 부풀어 보이면 된다.
```

경계의 의미는 하나다. **제출 완료 응답을 받은 사용자는 이미 경계 안에 있다.**
유실 가능 구간은 응답을 아직 받지 못한 요청뿐이고, 그 범위는 admission semaphore가 상한으로 묶는다.

### 거절은 애플리케이션이 아니라 엣지에서 일어났다

1,000/s에서 1.06%가 거절됐다.

| 지점 | 기준 | 한도 | 응답 | 실측 발동 |
|---|---|---:|---|---:|
| nginx `limit_conn` | 동시 프록시 연결 | 3,000 | 503 | **1,059** |
| 사용자 쿨다운 | 직전 제출 이후 경과 | 2,000ms | 429 + Retry-After | 366 |
| bulk admission | 동시 처리 중 제출 | 800 | 503 + Retry-After | 0 |
| completion 큐 | 큐 깊이 | 64 | CallerRuns (거절 아님) | 0 |

이전 기록에서는 같은 부하에서 **연결 8,246개가 그냥 끊겼다.** 애플리케이션은 멀쩡한데 nginx
연결 테이블이 먼저 무너진 것이다. `limit_conn` + `limit_conn_status 503`으로 고쳤고 이번 런에서
드롭 0건, 503 1,059건으로 확인했다. 드롭이 최악인 이유는 제출이 접수된 뒤 끊겼는지 클라이언트가
알 수 없기 때문이다. 중복 제거는 바이트가 같은 코드만 잡으므로, 사용자가 코드를 고쳐 재제출하면
두 번 채점된다.

## 노드 하나가 죽으면

백로그가 없는 조건(도착 100/s, 용량의 67%)에서 judge 노드 하나를 SIGKILL했다.
백로그를 걷어내야 재전달 자체의 속도가 보인다. 무주입 런과 짝지었다.

| 제출 100/s | 무주입 | judge-1 SIGKILL |
|---|---:|---:|
| p95 | 0.556s | 6.864s |
| p99 | 2.308s | 7.681s |
| **max** | 2.553s | **9.770s** |
| submissions = results | 19,452 ✓ | 19,493 ✓ |

**판정 근거는 max 하나다.** 노드는 60.3초 동안 죽어 있었다. RabbitMQ가 하트비트 타임아웃(기본
60초)을 기다렸다면 그 노드가 물고 있던 메시지의 end-to-end가 60초를 넘었어야 한다. max가 9.77초다.

```
 96s  ready=  0  unacked=17  consumers=32   ← SIGKILL 직전
100s  ready= 52  unacked=16  consumers=16   ← 4초 만에 회수 완료
157s  ready=567  unacked=32  consumers=32   ← 다시 소비 시작
```

SIGKILL로 TCP가 끊기자 broker가 곧바로 감지해 미확인 메시지를 큐로 되돌렸다.
`unacked=16`은 살아남은 노드의 consumer 16개가 각각 1건씩 쥔 포화 상태다.

꼬리가 나빠진 것은 재전달 지연 때문이 아니다. 죽어 있던 60초 동안 용량이 반토막나 `ready`가
703까지 쌓였고, `703 ÷ 150 = 4.7초`에 채점 시간이 붙어 7~10초대가 된다. 관측값과 맞는다.
**p95·p99·max 악화분은 전부 "능력이 없던 시간"이다.** 복구 영향을 줄이려면 broker가 아니라
JVM 기동 시간이나 노드 수를 손대야 한다.

## `INSERT IGNORE` 뒤에 숨는 누락

> 중복 한 건이 chunk 전체를 rollback시키는 것을 막으려고 제출 저장을 `INSERT IGNORE`로 바꿨다.
> 그런데 `INSERT IGNORE`는 unique 충돌만 무시하지 않는다. FK 위반처럼 행 전체가 경고와 함께
> 조용히 사라지는 경우도 삼킨다. user 사전 조회를 없애고 `getReferenceById()`로 바꾼 뒤로는
> 존재하지 않는 user가 FK 위반으로 드러나는데, 이게 "정상 중복"과 구분되지 않았다.
>
> 게다가 Connector/J가 batch를 multi-values로 rewrite하면 JDBC update count가
> `SUCCESS_NO_INFO(-2)`로 온다. **어떤 행이 삽입되고 어떤 행이 무시됐는지 드라이버가 알려주지 않는다.**
>
> 그래서 INSERT 직후 같은 트랜잭션에서 예약 ID와 dedup key를 다시 조회해 분류한다.
>
> | 조회 결과 | 판정 | 처리 |
> |---|---|---|
> | 예약 ID에 같은 key의 행 존재 | 새 삽입 | 예약 ID 반환, judge outbox 생성 |
> | 예약 ID 없음 + 같은 dedup key 행 존재 | 정상 중복 | 기존 submission ID 반환 |
> | 둘 다 없음 | 설명 불가 누락 | 정합성 예외 → rollback |
> | 예약 ID가 다른 key의 행을 가리킴 | ID 충돌 | fail-fast → rollback |
>
> 여기서 끝내면 불량 한 건이 여전히 정상 99건을 죽인다. 정합성 예외에 문제가 된 예약 ID를 담고
> chunk를 둘로 나눈다. **offenders**(예외가 지목한 요청 + 같은 dedup key를 공유하는 요청)의
> Future만 실패시키고, **survivors**는 이미 예약해 둔 같은 ID로 한 번만 다시 insert한다.
> 첫 시도가 rollback으로 완전히 취소됐고 ID가 고정되어 있으므로 재실행이 안전하다.
> 재실행에서는 다시 격리하지 않아 chunk당 DB 시도는 최대 2회다.

이 판별 덕분에 MySQL이 중복의 유일한 권위가 됐고, 앞단에 두던 Redis 중복 캐시를 임계 경로에서
지울 수 있었다.

# 3. 스코어보드 전달·복구 경로

**스코어보드 전달을 DB outbox에서 RabbitMQ stream으로 옮겼다. 이유는 처리 성능이 아니라
checkpoint의 위치다.** Redis 상태와 재시작 지점이 같은 스냅샷 경계 안에 있어야 복구가 단순해진다.

Redis 스코어보드는 파생 상태다. 그래서 "Redis가 죽으면 어떡하나"는
**"어디서부터 다시 흘려보낼 것인가"** 한 줄로 좁혀진다. 그 재시작 지점을 어디 둘지가 문제였다.

가장 단순한 발상인 `max(outbox.id)`는 쓸 수 없다. auto increment ID에는 gap이 있고,
DB insert 순서와 Redis 적용 순서가 같지 않으며, 실패한 작은 ID가 재시도되는 동안 큰 ID가
먼저 적용될 수 있다. 하나만 저장해서는 중간 누락을 판단할 수 없다.

문제를 다시 쓰면 **단조 증가 키를 누가 소유하는가**다.

```
기존   Redis INCR(redis_seq)  →  DB outbox에 checkpoint
현재   RabbitMQ가 offset 발급  →  Redis Lua 안에 checkpoint
```

```
[그림 4] 스코어보드 전달 경로 — 좌우 비교

  좌: DB outbox                        우: RabbitMQ stream
  Judge 결과 commit                     Judge 결과 commit 후 publish
  → contest_submission_outbox          → RabbitMQ stream (broker가 offset 발급)
  → Batch worker 주기 claim             → Batch consumer
  → Redis Lua                          → Redis Lua — 한 번에 원자적으로
    (INCR redis_seq + 스코어보드)           (스코어보드 + offset + db-pending)
  ⤴ redis_seq를 DB로 되돌려 기록 (점선)

  하단 결론 상자
  좌: checkpoint = DB의 redis_seq → Redis만 되감기므로 어긋남을 탐지해야 한다
  우: checkpoint = Redis 안의 offset → 되감긴 offset + 1 이 곧 재시작점

  왼쪽에만 되돌아오는 점선이 있다는 비대칭이 이 그림의 전부다.
```

## 두 방식이 공유하는 전제

어느 쪽을 고르든 얻는 것이 하나 있다. **RDB 스냅샷으로 복구했을 때 그 시점 이후 구간만 다시
Redis로 흘려보내면 된다.** 스코어보드 전체를 MySQL에서 재구성할 필요가 없다.

- outbox 방식은 DB에 남아 있는 미완료 행을 다시 `PENDING`으로 돌려 재적용한다
- stream 방식은 되감긴 offset 다음부터 broker가 그대로 다시 흘려준다

전체 rebuild는 retention 밖으로 밀려났을 때만 쓰는 마지막 수단이고, 평상시 복구는 증분으로 끝난다.
이게 가능한 이유는 뒤의 재적용 안전성 때문이다. 차이는 **그 증분의 시작점을 얼마나 쉽게 찾느냐**다.

## 무엇을 지불했나

전달 구조로는 stream이 더 맞지만 대가가 있다. judge는 결과를 commit한 뒤 stream publish confirm까지
기다린 다음에야 work queue를 ACK한다. **DB와 broker에 두 번 쓰는 비용**이고, 그 사이 장애는
중복 전달로 나타난다.

```
contest_submission_result commit
  → result stream publisher confirm
  → judge work queue ACK
```

이 순서를 바꾸면 안 된다. publish를 commit 앞에 두거나 confirm을 기다리지 않고 listener를 반환하면
"DB commit 후 publish 전 장애"를 재전달로 복구할 수 없다. 재전달됐을 때는 결과 행부터 조회하고,
이미 있으면 **채점 API를 호출하지 않고 저장된 결과만 다시 발행**한다. unacked delivery를 가진
consumer connection을 강제로 끊어 확인했다 — 결과 행은 그대로였고 stream entry만 하나 늘었으며
채점 호출은 0회였다.

스코어보드 적용이 순서·중복에 무관하므로 그 중복 entry가 결과를 바꾸지는 않는다.
Redis 적용과 MySQL 완료 표시 사이의 틈은 Lua가 offset과 함께 기록하는 `db-pending` set으로 메운다.
그 사이에 죽으면 재전달이나 다음 기동의 복구 루틴이 같은 batch update를 반복한다.

## 복구 제어 흐름

```
outbox   Redis가 K로 롤백 → 주기 스캔 → 어긋남 탐지 → DB requeue → 재적용
stream   상태와 offset이 함께 K로 롤백 → offset 역행 감지 → K+1부터 직접 replay
```

consumer를 멈추고 스냅샷 K를 만든 뒤 제출 tail 약 90건을 더 적용한 상태 N의 스코어보드 전체
digest를 기록한다. Redis를 SIGKILL하고 K의 RDB로 되돌린 다음, digest가 N으로 돌아올 때까지 잰다.
일부 key만 지우는 시험이 아니라 스코어보드와 checkpoint가 함께 되감기는 롤백이다.

| | 수렴 시간 |
|---|---|
| stream | 2초대 |
| outbox | 31초 |

outbox는 Redis와 DB 사이의 어긋남을 **찾아야** 하고, 그 탐지가 주기 스캔이라 복구 시간의 하한을
만든다. stream은 되감긴 offset이 곧 재시작점이라 탐지 단계가 없다.

## 다시 흘려보내도 안전한가

위 복구가 성립하려면 재적용이 안전해야 한다. 그런데 처음 구조는 그렇지 않았다.

```
채점 완료 순서 ≠ 제출 순서
  t=10분  WRONG    (채점 2초)
  t=12분  ACCEPTED (채점 10ms)      → 도착은 ACCEPTED 먼저

              실시간 Redis    DB 재구성
  penalty          12            17      ← 참가자가 본 순위 ≠ 최종 순위
```

`accepted` 플래그와 오답 수를 누적하고 정답이 오면 그 시점 값으로 penalty를 확정하는 방식은,
이벤트가 제출 순서대로 도착한다는 가정을 숨기고 있었다. 늦게 온 오답은 버려졌다.

누적을 버리고 지금까지 본 제출 사실 자체를 보존한 뒤, 이벤트마다 그 문제의 기여도를 처음부터
다시 계산하도록 바꿨다. 같은 오답이 중복 도착하면 같은 필드를 덮어쓰고, 더 이른 정답이 늦게
도착하면 정답 시각을 교체하고 다시 계산한다. summary에는 이전 기여도와의 **차이만** 더한다.

회귀 테스트로 세 가지를 고정했다. 위 시나리오의 최종 penalty가 17일 것,
같은 이벤트 집합을 무작위 순서로 적용해도 결과가 같을 것,
실시간 Redis 경로와 MySQL 재구성 경로가 같은 순위를 낼 것.

## 성능은 판단 근거가 아니었다

두 구현을 같은 조건에서 2회씩 측정했다. 단위는 ms다.

| | outbox | stream |
|---|---:|---:|
| 스코어보드 반영 p50 | 403 / 417 | 326 / 321 |
| 스코어보드 반영 p95 | 617 / 780 | 543 / 547 |
| 적용 구간 p95 | 303 / 299 | 168 / 157 |
| Redis pipeline p95 | 7.9 / 8.6 | 9.3 / 9.3 |
| Lua 오류 | 0 / 0 | 0 / 0 |

stream이 중앙 경로에서는 조금 짧고 Redis pipeline에서는 조금 길다. **어느 쪽도 상대를 밀어낼
정도가 아니다.** 성능이 비슷하다면 남는 판단 기준은 복구 특성이고, 거기서는 차이가 분명했다.

# 4. 남은 한계

**채점이 `Thread.sleep`이다.** 설계 전제인 긴 꼬리는 기본 50ms에 p95 2초를 주입해 재현했고
`prefetch` 실험도 그 조건에서 했다. 다만 sleep은 블로킹 시간만 흉내 낼 뿐 커넥션 풀 고갈,
타임아웃, 부분 실패를 모델링하지 않는다. 실제 채점 서버를 붙이면 실패 모드가 하나 더 생긴다.

**RabbitMQ가 단일 노드다.** stream replication, leader failover, replica catch-up을 검증하지 않았다.
3장의 복구 결론은 단일 노드에서 Redis가 되감긴 경우에 대한 것이다.

**대회 제출과 일반 제출이 같은 파이프라인을 쓴다.** 대회 중에도 일반 제출은 계속 들어오고,
일반 제출은 전체 테스트케이스를 돌리므로 한 건에 30초까지 걸릴 수 있다고 가정한다.
`prefetch=1`은 consumer 하나가 한 건만 쥐게 하지만 **그 하나가 30초를 쥐고 있는 것 자체는 막지 못한다.**
consumer 32개 중 몇이 일반 제출에 물려 있으면 대회 제출의 실효 용량이 그만큼 줄고, 위에서 본
`ready ÷ 처리율` 관계 그대로 대회 제출의 꼬리가 늘어난다. 큐를 분리하거나 대회 제출에 별도
consumer 풀을 주는 것이 다음 과제다. 아직 측정하지 않았다.
