## 한 줄 소개

**부하와 장애를 먼저 가정하고, 그 가정이 맞는지 지표로 확인한 뒤 구조를 고치는 개발자입니다.**

온라인 저지(Online Judge) 서비스를 혼자 설계·구현하면서, 대회 중 제출이 몰릴 때
데이터가 유실되거나 순위가 어긋나지 않게 만드는 일을 주제로 삼았습니다.
"동작하는 코드"가 아니라 **"어떤 장애까지 견디는지 말할 수 있는 코드"**를 목표로 했습니다.

---

## 핵심 역량

### 1. 정합성을 순서와 중복에 의존하지 않게 설계합니다 — [3장](03-scoreboard-delivery.md)

채점 완료 순서는 제출 순서와 다릅니다. 이 사실을 무시한 누적 방식 스코어보드는
실시간 순위와 대회 최종 순위를 다르게 만들었습니다.
누적을 버리고 **제출 집합에서 기여도를 매번 다시 계산하는 방식**으로 바꿔,
이벤트 도착 순서와 중복 전달 횟수에 무관하게 같은 결과로 수렴하도록 만들었습니다.
같은 데이터에서 실시간 경로와 DB 재구성 경로가 일치하는 것을 회귀 테스트로 고정했습니다.

### 2. 추측이 아니라 측정으로 병목을 찾습니다 — [2장](02-submission-pipeline.md)

"Redis가 느리다"고 생각했지만, Redis 서버의 `HGET` 실행시간은 0.72µs였습니다.
JFR로 확인한 실제 문제는 **CPU가 포화된 상태에서 동기 호출을 기다리며 park된
Java 스레드**(평균 141ms, 최대 1,240ms)였습니다.
원인을 잘못 짚었다면 Redis를 튜닝했겠지만, 실제 해결책은 Redis를 정확성 경로에서
제거하는 것이었습니다.

### 3. 성능 수치가 근거가 되지 못할 때를 구분합니다 — [3장 5절](03-scoreboard-delivery.md)

스코어보드 전달 경로를 RabbitMQ Stream으로 바꾸면서 두 구현을 부하 테스트로 비교했지만,
반복 실행이 부족해 성능 차이는 **통계적으로 확정할 수 없다고 판단**했습니다.
채택 근거를 성능이 아니라 **복구 불변식이 단순해진다는 점**으로 명시하고,
남은 검증 항목을 production 전환 게이트로 문서에 남겼습니다.

## 기술 스택

| 분류 | 사용 기술 | 사용 맥락 |
|---|---|---|
| **언어 · 프레임워크** | Java 17, Spring Boot 3.4.3 | 역할별(web/batch/judge) 프로필 분리 기동 |
| **데이터 접근** | Spring Data JPA, Hibernate, **JDBC Template** | JPA의 `merge` 경로 문제를 확인한 뒤 임계 경로는 JDBC batch로 전환 |
| **RDBMS** | MySQL 8.0 | `INSERT IGNORE`, `FOR UPDATE SKIP LOCKED`, `rewriteBatchedStatements` |
| **캐시 · 인메모리** | Redis 7 | 스코어보드 파생 상태, Lua script 원자적 갱신, rate limit |
| **메시징** | RabbitMQ 4.1 | quorum queue(작업 분배), stream queue(offset 기반 복구), publisher confirm, DLQ |
| **인프라** | Docker Compose, Nginx | 9개 컨테이너 역할 분리, CPU/메모리 상한 고정 |
| **성능 · 관측** | Gatling 3.10.5, Prometheus, Grafana, **JFR** | 부하 모델링, 구현 중립 지표 설계, 스레드 park 분석 |
| **빌드 · 마이그레이션** | Gradle 8.12.1, Flyway | |
