# 1. 인서트 성능 개선

대회 제출 하나당 3인서트, 1업데이트 쿼리가 필요해서 부담이 크다.

## 1.1. PS (Prepared Statement)
- 기본적인 jpa사용하면 적용되는데 **파싱에서 AST 생성까지, SQL 텍스트 전송 등 비용**을 줄일 수 있다. 
  기준으론 최적화부터는 다시 한다.

## 1.2. 그룹커밋
- 그룹커밋은 디비에서 **트랜잭션이 거의 동시에 커밋에 도달**하면 로그를 묶어서 **fsync**하는 최적화. 
   
  `innodb_flush_log_at_trx_commit` : 디비에서 리두 로그 저장 과정에서 fsync 하는 빈도
  기본 1에 0,2로 바꾸면 클라이언트에 **OK 송신 후에도 데이터가 날아갈 수 있어** 치명적이라 1로 유지.

  `sync_binlog` : 디비에서 빈로그 저장 과정에서 fsync 하는 빈도
 복제, PITR(특정시점 복구), 재샤딩** 같은 기능에서 사용

- 전자만 있어도 **로컬 내구성**은 챙길 수 있고 후자의 기능은 성능을 위해 포기 가능이라 생각. 
   syncbinlog = 0이나 n으로 조정. 

- fsync 전 write까지는 **OS 캐시**에 저장되어 유실 가능하다고 한다.

## 1.3. 배치
- ### 1.3.1. 배치가 묶이기 전 **각 insert의 실패를 추적**  
   **insert문 합칠 수 없다** 이러면 속도에서 메리트가 떨어진다.
- 이때 다른 테이블에 일단 넣고 나서 처리를 하고 거기서 몇몇 row만 insert하는 방식도 있다. 
  하지만 insert시 로직으로 실패하는 경우는 거의 없다 예상해서 보류.

- ### 1.3.2. 배치를 하나의 트랜잭션으로(하나 실패하면 다 실패)  
- insert문을 하나로 **rewrite 가능**.
- (userid, problemid, codehash) **유니크 제약** 존재.
캐시로 해당 유니크 제약을 미리 한 번 필터링하고 insert하는 구조로 진행.  
- **AUTO_INCREMENT**사용하면 의미가 없다.
 **Spring에서 PK를 생성**하는 구조로 바꾸었다. 키가 UUID 같은 값이면 **랜덤 insert**로 비용이는다.
  Snowflake 같은 **단조증가**에 가까운 키 필요. 
  하지만 지금 spring 하나라 **1,2,3,4...을 로컬에서 생성**해서 PK로 사용.  
 `contestsubmission`에서 pk생성하고 `contestsubmissionresult`, `outbox`에서 **키를 그대로 사용**한다.  

### 쿼리 rewrite 적용
- **JDBC 드라이버의 preparedStatement 배치에서 rewrite가 적용**된다.  
  이를 위해서는 **직접 호출**하거나 **같은 트랜잭션/EntityManager**에서 실행 돼야함.  
- 따로 queue에 모아주고 100건 이 넘으면 insert하고, 0.2초마다 queue에서 빼내서 처리하는 구조를 만들었다.  
- 유저가 제출했을 때 **제출 완료라 뜨고 제출이 실패하는 것**은 치명적이기에 **블로킹**으로 만들었다.  
- 대회시 제출에 **0.2초 지연**이 추가되는 것은 감수할만 한 트레이드오프라고 생각.

## 1.4. redis갱신 시점 이슈
- `userId, 1
- problemId, hash` 유니크 제약을 Redis에서 확인할 때 **Redis 갱신 시점**에 대한 이슈.  
  **Redis를 중복 확인하고 바로 갱신**하면 이후 **DB 트랜잭션이 실패했을 때**도 같은 입력이 Redis에서 걸러진다. **트랜잭션 실패 후 Redis 삭제도 Redis만 실패**가능.  **치명적**인 로직 오류가 생길 수 있다.
  **Redis를 DB 트랜잭션 성공 후 갱신**하면 **트랜잭션 성공 전까지 중복 입력**이 들어올 수 있다.  

### 1 기존 후자
결국 작동은 할텐데 중복입력의 실패로 100건씩 실패할거라 **비용이 크다.** **로직상은 문제없다.**  
사용자가 제출 성공을 하고 제출이 날아가거나 제출한 적 없는 내용을 제출하지 못하는 것보단 낫다.

### 2 레디스 추가 필터
**추가적인 트랜잭션 전에** Redis에 **SETNX + TTL**로 같은 제출에 대해 **필터를 한 번 더**하고 이를 **트랜잭션 완료 후 기본 중복 체크 먼저 업데이트**하고 **지우는 방식**이 있다.  
이때 **SETNX를 지우는 것에서만 실패**할 수도 있고 **트랜잭션이 실패해도 SETNX을 지워야** 할 텐데 여기서 실패해도 제출이 잘못 필터링된다. 그래도 **TTL**로 언젠간 다시 입력받을 수 있을 것이다.

### 3 분산 트랜잭션
**2PC는 Redis에서 구현이 힘들고** 지금처럼 **QPS 높은 상황**에서는 적합하지 않다.  
**Saga나 TCC**는 **결과적 일관성**을 목표로 해서 성능은 낫지만 **무리가 있다. 구현 자체도 힘들다.**

# 2. rank 조회 개선

- 정렬된 유저목록을 불러오고 내가 포함된 페이지로 이동하는 기능 지원
- 유저가 1000만 수준이라 뒤의 유저가 내가 포함된 페이지로 이동하는 기능을 이용할때 그냥 구현하면 오래 걸릴 수 있다.

---

## solvedcount
- **solvedcount는 1씩 증가**
- 푼 문제수, 해당하는 문제만큼 푼 유저수, 더 많은 문제를 푼 유저수 를 저장하는 solved bucket 관리.
- solvedcount 갱신시에 자신이 해당하던 버킷과 새로 해당할 버킷만 갱신하면 끝.

- 자신의 solved count로 solvedbucket에서 자신보다 solvedcount가 높은 유저 수를 알 수 있다.
- 자신의 solvedcount로 조건을 걸어 같은 값의 유저 중 몇 등인지 알 수 있다.
- 위 정보로 자신이 총 몇 위인지 알 수 있고 이를 통해 페이지 시작 랭크를 계산할 수 있다.
- 해당유저부터 페이지 사이즈 만큼 구해오면 된다.

- 기존 최대 1000만 offset에서 solvedcount 같은 유저 수 offset 2번으로 개선 됐다.
- solvedcount 0인 경우가 50퍼 정도도 가능 이때 부하가 여전히 크다. 그런데 0인 경우 순위가 의미 없다 생각해 solvedcount가 0이 아닌 유저 중에 
pagesize-1명의 꼴지를 구해오고(효율적) 거기에 자신을 붙이는 식으로 구현.
- 1문제만 푼 경우도 최대 5퍼정도 예상하는데 정말 최악에 상황에서 offset50만인거라 아마 충분하다고 생각된다.(1초 미만예상)
- 이 방식에서는 전체 row 수를 bucket 1에서 1에 해당하는 유저와 보다큰 유저 합치면 알 수 있다. (어차피 0인 경우에는 기본적으론 순위표에 없기때문.)

---

## current streak
현재 이어가고 있는 연속해서 문제를 푼 날짜 수.
- **스트릭은 하루에 한 번 갱신**
- 일일 활동 유저 10만 정도를 가정했기에 current streak이 0이 아닌 유저도 그정도.
- streak을 배치로 갱신하는 시점에 0이 아닌 유저만 모아서 미리 계산.
- streak 자체는 lazy하게 갱신하는 구조도 생각했었는데.
전날 스트릭이 0이 아니었던 유저의 수도 10만이라 최대 20만유저의 스트릭만 수정하면 되기때문에 바로 갱신한다.
- 0인 유저가 조회할 경우 위와 같이하면 된다.
- 가장큰 rank가 전체 row 수가 된다.

---

## longest streak
- **1씩 증가 + 하루에 한 번 갱신**
- 이 값은 위 두 칼럼의 특징을 공유해서 배치시에 solvedcount와 같이 bucket을 갱신하는 방식으로 구현했다.
- 그런데 배치의 시간은 위가 짧겠지만(longest streak바뀐유저만 갱신되므로) 평소 조회시에 위의 current streak처럼 순위를 저장한 테이블을 만들면 조회가 무척 빠를 것이다.
- solvedcount가 1인 유저보다 longeststreak이 1인 유저가 같거나 많아서 두 트레이드 오프에서 잘 결정해야할 것.
- 전체 row 수는 각 방식에 맞게 위 처럼 구할 수 있다.

# 3. 스트릭 배치 

## daily active user

- 특정 날짜에 문제를 푼적이 있는 유저를 저장한다.
- 하루동안 dau를 갱신하다가 12시가 지나면 이를 바탕으로 스트릭을 계산한다.
- 이를 위해 레포지토리에서 `deleteOrderThan`이란 메소드를 지원하는데
- 한 번에 삭제할때 **nextkey락**을 걸면 해당 날짜 전날의 row를 삭제할때 해당 날짜이상의 row가 없었다면 모든 upsert가 대기하고 있었다면 day, userid가 그보다 작은 upsert는 대기하게 된다. 이는 10만건 정도 기준으로 1-3초정도 걸릴수 있기에 이를 막고자 트랜잭션의 격리수준을 **readcommited**로 낮추고 진행했다.

---

## batch

- 매일 00.05쯤 전날의 dau를 이용하여 스트릭을 갱신한다.
- 스트릭을 보고 longest streak bucket또한 갱신한다.
- 이때 유저의 갱신이 베타락을 걸어 다른 곳에서 병목이 되는데 이것이 배치 끝날때 까지이다.
- 이걸 해결하기위해 결과적으론 배치를 500개정도 씩 끊어서 트랜잭션을 작게 유지하는 것으로 로직을 바꾸었다.
- 이들을 갱신하는 내용을 jpa로 바꾸어서 update를 미뤄 락이 늦게 걸리게 하고 맨 마지막에 한번에 쿼리만 실행하는 동안만 락이 걸리게 구현하는 것을 고려했었다.
- 로직상 문제가 있을 수 있는데 유저의 스트릭 갱신과 longest bucket의 갱신은 여기서 밖에 안했어서 가능은 하다고 생각되는데 그러면 실제로 더티체크하기 전까지 유저에 락이 안걸릴 것이다.
- longest bucket은 같은 엔티티를 여러번 수정한 거라 효과가 큰데 유저는 각각의 유저라 쿼리를 모은 효과만이 있었다. 하지만 그래봤자 수십초가 걸릴수도 있다고 하기 때문에 결국 쪼개는 방식으로 구현할 수 밖에 없었다. 유저갱신이나 수정이 1분씩 대기할 수도 있기 때문에.
- 생각해보니 스트릭을 유저 테이블에서 분리하면 배치중에 락이 걸리는 시간을 엄청 줄일수 있을 것.

# 4. 일반 제출


## submission

- `submission`에는 `userId`, `problemId`, `codeHash` 에 대한 **유니크 키 제약**이 있음.
- 로직상으로는 **유저·문제·코드**가 중복이 되면 안되지만 `code`는 **LONGTEXT**라 중복 검사가 수월하지 않아 **hash 함수**를 이용하고, 혹시 중복이 있을 때 **코드도 같으면 앞에 `#1`** 이런 식으로 붙여서 해시키 새로 만드는 **재시도**를 함.

---

## 목록 조회 (필터/정렬)

- `submission` 목록을 불러올 때 다음 필터/정렬을 제공한다.
  - **유저이름(username)**
  - **문제 id**
  - **id 오름/내림 정렬 순서**
  - **맞은 결과만 포함** 필터

- `username`은 실제로 사용한다면 **특정 유저를 조회**하는 기능이 실질적으로 필요한 기능이라 생각해 **eq로 비교**한다.
- 또한 `username`을 그대로 조건으로 사용할 경우 **조인이 꼬이거나** 할 수 있어서,
  - **username만 먼저 검색**해주고(유니크 제약도 있음 `username`에)
  - **id를 가져와서** 효율적으로 실행될 수 있게 한다.

---

## 인덱스/스케일 가정

- 이때 이 쿼리를 위해서 **인덱스**를 고려하는데 `submission` 테이블은 **2억 row**까지도 고려했다.
- 그런데 이때 목표치가 **유저 카디널리티가 1천만**이라 한 유저에 대해 **평균 20**, **최대 1000 row** 정도라고 한다면
  - `(userId, id)` 인덱스만 있어도
  - `userId, problemId, result, id` 이게 필요한 쿼리도 그렇게 오래 걸리지 않고 수행할 수 있을 것이다.
- **problem**으로 검색할 때는
  - `(problemId, id)`
  - `(problemId, result, id)` 따로 있는 편이 좋을 것이다.

## judgement

## normalSubmission

- 어떤 유저가 **특정 문제를 처음 맞추었을 때** `solvedCount`, `solvedBucket`, `DAU`, `acceptedSubmission` 이것들을 **갱신**해주어야 한다.
- 어떤 유저가 **같은 문제를 여러 번 풀었을 때** 이러한 과정이 **중복 실행되면 안되기 때문에** `acceptedSubmission` **PK가 `(problemId, userId)`** 를 이용해서 **차단**해준다.
- 또한 **같은 유저가 다른 ‘처음 푼 문제’**가 있을 때 문제가 있을 수 있는데 이것을 막기 위해 **`userGuard`를 만들었다.**
  - 해당 테이블에 **비관락**을 건다.
  - 지금 같은 유저의 **다른 문제 첫 풀이가 겹치는 경우는 거의 없다고 생각**해서 진행했다.
- **낙관락**을 걸어도 간단히 해결되고 경쟁이 거의 없지만,
  - **낙관락이 필요 없는 user에 대한 갱신에 version 관리의 비용**이 느는 것이 마음에 들지 않았다.
- **비관락**을 건다면 지금 `submission` 말고 **다른 곳에서 유저가 락에 대기**할 수도 있기에 꺼려졌다.
  - **`userGuard`를 만들어서** 위와 같은 문제를 줄이고 **정확히 락이 걸려야 할 부분만 락**을 걸 수 있고 **다른 곳에 영향을 주지 않을 수 있었다.**
- 또한 **`dailyActiveUser`의 갱신을 UPSERT로 원자적으로 묶어** 추가적인 락 없이 진행한다.

## 최종 방안 (outbox + 단조 증가 key)

- 레디스에서 기본적으론 **rdb로 백업**하고 **단조증가하는 key**를 발행하고 **아웃박스에 칼럼**을 추가해서 이 key를 저장하면
- 만약 중간에 redis가 죽었다가 rdb로 복구되고 날아간 내용이 있어도 결국 **아웃박스에 key가 중복되어서 저장**될 것이므로 **멱등성**을 보장하고
- spring에서 **주기적으로 key가 중복된 outbox를 다시 레디스로 보낸다면** **오랜 괴리 없이 스코어 보드가 유지** 될 것이다.
