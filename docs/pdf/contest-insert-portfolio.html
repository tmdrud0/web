대회 제출 저장 경로 최적화

JPA batch rewrite를 실제로 작동시키도록 경로를 재구성해, 대회 중 가장 먼저 맞는 insert 병목을 줄였다.

Context
온라인 저지 대회 제출 저장
Goal
고부하 처리량 개선과 원인 검증
Validation
Gatling step-load, 첫 실패 RPS 비교

문제 정의

왜 이 경로를 먼저 봤는가

대회 제출은 사용자가 응답 품질을 가장 빠르게 체감하는 경로다. 대회 시간에는 같은 경로로 트래픽이 몰리고, 이 insert가 흔들리면 이후 채점과 스코어보드까지 연쇄적으로 영향을 받는다.

초기 진입점 트래픽 집중 지연 전파 위험

최적화 목표

  • 대회 제출 저장 경로의 처리량을 높인다.
  • DB round-trip과 커넥션 점유 시간을 줄인다.
  • 왜 빨라졌는지 실행 단위까지 설명 가능한 상태로 남긴다.

핵심 접근

1. 요청을 큐에 모아 같은 flush 단위로 묶기

여러 요청을 같은 트랜잭션과 같은 EntityManager 안에서 처리하도록 큐와 chunk를 도입했다. 이렇게 해야 JDBC batch와 MySQL의 rewriteBatchedStatements가 실제로 multi-values insert 형태로 합쳐진다.

2. persist 기반으로 신규 insert 경로 고정

ID를 애플리케이션에서 먼저 할당하는 구조와 saveAll(...)이 만나면서 merge 경로가 열렸고, row마다 추가 조회가 붙고 있었다. 이를 entityManager.persist(...)로 바꿔 불필요한 select를 제거했다.

결정적 포인트

성능 차이는 단순히 batch 옵션을 켰기 때문이 아니라, 같은 트랜잭션 경계 안에서 batch rewrite가 의미 있게 동작하도록 경로 전체를 정리했기 때문에 나왔다.

시각화: 첫 실패 RPS 비교

표 대신 시나리오별 임계 처리량을 grouped bar chart로 재구성했다. 오렌지는 기존 immediate insert, 청록은 bulk insert 경로다.

Immediate Bulk

커넥션 풀이 작은 환경일수록 개선 폭이 더 컸다. 특히 insert가 3회로 늘어나는 시나리오에서 bulk 경로가 병목 전파를 크게 늦췄다.

왜 빨라졌는가

기존 경로의 손실 지점

  • 저장 전 조회가 섞여 커넥션과 트랜잭션을 오래 점유했다.
  • lazy 로딩이 worker 내부에서 예상 밖 추가 SELECT를 만들었다.
  • OSIV로 인해 커넥션 사용 구간이 더 넓게 퍼졌다.
  • saveAll 기반 merge 경로가 신규 insert에도 row 단위 조회를 추가했다.

정리 후 바뀐 점

  • 큐 적재 전후의 책임을 분리해 긴 점유 구간을 잘랐다.
  • persist 기반 insert로 신규 저장 경로를 명확하게 고정했다.
  • 같은 flush 단위에서 multi-values insert가 실제로 만들어졌다.
  • round-trip 감소가 커넥션 풀이 작은 환경에서 더 크게 체감됐다.

정리

핵심 결론

DB 작업이 무겁고 커넥션 자원이 제한적일수록 bulk insert의 이점은 커진다. 단, 단순히 batch 옵션만 켜서는 부족하고, 요청 수집 방식과 트랜잭션 경계까지 함께 설계해야 실제 성능 이득으로 이어진다.

성능 비교 기준은 모두 Gatling step-load의 첫 실패 RPS이며, insert 3건 시나리오는 제출 1건당 보조 insert 2회가 추가되는 부하 프로필로 검증했다.
