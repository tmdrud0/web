Portfolio 03

Redis Scoreboard Recovery

Redis가 과거 스냅샷으로 복구돼도 유실 반영을 다시 찾을 수 있도록, 적용 순서와 복구 신호를 분리해 설계했다.

Issue
Redis 복구 후 DB와 scoreboard 상태 불일치
Key Design
duplicate redis_seq를 복구 신호로 사용
Outcome
운영 중 자연 복구 + 종료 시 정합성 보정

문제 정의

왜 outbox.id만으로 부족했는가

outbox.id는 DB insert 순서이지 Redis 적용 순서가 아니다. 실패와 재시도로 중간 id가 비어 있을 수 있고, Redis가 예전 스냅샷으로 복구돼도 DB의 id는 되돌아가지 않는다. 그래서 Redis 입장에서 유실을 자연스럽게 감지하기 어렵다.

설계 목표

  • 평소 운영에서는 별도 복구 모드 없이 자연스럽게 회복한다.
  • 복구 신호는 Redis가 스스로 노출할 수 있어야 한다.
  • 대회 종료 시에는 한 번 더 명시적으로 정합성을 맞춘다.

핵심 아이디어

적용 키와 복구 키를 분리

outbox.id는 멱등 적용 키로 남기고, 별도로 Redis가 발급하는 redis_seq를 두었다. redis_seq는 Redis 관점의 적용 순서를 의미하므로, snapshot rollback 이후 중복 발급이 복구 신호가 된다.

중복 seq를 발견하면 replay

Redis가 과거 상태로 돌아가면 seq counter와 contestSubmissionId 매핑도 함께 과거로 돌아간다. 이후 새 반영이 들어왔을 때 예전 seq가 다시 발급될 수 있고, batch 서버는 이 duplicate redis_seq를 찾아 누락 구간을 다시 밀어 넣는다.

핵심 문장

이 구조의 본질은 유실 여부를 DB 기준으로 추론하지 않고, Redis가 스스로 드러내는 이상 신호를 복구 트리거로 사용한 것이다.

대안 비교

DB gapless seq

복구 기준이 DB에 영속되므로 명확하지만, gapless 발급 구간을 직렬화해야 하고 여러 서버에서 다루기 어려워진다.

정합성 강함 발급 병목 가능

명시적 복구 절차

현재 max seq를 읽어 그보다 큰 outbox를 다시 보내는 방식이다. 범위는 명확하지만 운영에서 장애 감지와 복구 시작을 별도로 관리해야 한다.

복구 범위 명확 운영 절차 추가

선택한 방식: 자연 복구

평소처럼 outbox를 계속 처리하면서 duplicate redis_seq를 감지한다. 운영 흐름을 끊지 않으면서, 복구가 필요한 순간만 batch replay가 개입한다.

운영 단순 복구 자동화
Page 1

복구 흐름 시각화

복구 로직을 텍스트 대신 흐름도로 정리했다. 핵심은 Redis가 과거 상태로 돌아왔을 때 duplicate redis_seq가 발생하고, 이 신호로 replay를 시작하는 지점이다.

Redis rollback이 발생해도, batch 서버는 duplicate redis_seq만 보면 복구가 필요한 시점을 알아낼 수 있다.

최종 운영 구조

평소 운영

duplicate redis_seq 기반 자연 복구를 사용한다. 별도 복구 모드 없이 기존 처리 흐름을 유지한다.

대회 종료 시

Redis의 max seq 기준 catch-up replay를 한 번 더 수행해 종료 시점 정합성을 맞춘다.

역할 분리

judge 서버는 결과와 outbox 저장, batch 서버는 반영과 replay, Redis는 빠른 조회용 파생 상태를 담당한다.

정리

핵심 결론

이 설계는 Redis를 완전히 신뢰하지도, 복구 절차를 무겁게 만들지도 않는다. 운영 중에는 자동으로 회복하고, 종료 시에는 명시적으로 정합성을 맞추는 절충안을 선택했다.
