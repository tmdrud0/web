Portfolio 02

Rank 조회 경로 최적화

1천만 유저 규모에서 around me 페이지가 버티도록, OFFSET 중심 조회를 rank 계산 중심 구조로 바꿨다.

Problem
깊은 페이지일수록 선형으로 커지는 OFFSET 비용
Idea
내 rank와 page start만 빠르게 계산
Scale
1천만 유저 기준 실행계획과 실측 시간 비교

문제 정의

병목은 정렬보다 OFFSET

정렬 인덱스를 잘 타더라도, 깊은 페이지에서는 앞 row를 계속 읽고 버려야 한다. 결국 around me에서 필요한 것은 모든 앞 페이지가 아니라 내 rank와 그 rank가 속한 page start다.

깊은 페이지 취약 선형 증가 around me 핵심

접근 전략

  • current streak: 배치로 미리 계산한 snapshot_rank를 읽는다.
  • solved: solved_count_bucket으로 tie group 범위를 빠르게 찾는다.
  • 둘 다 최종 단계에서는 필요한 페이지 구간만 읽는다.

구조 설계

Current streak: snapshot 기반 조회

하루 한 번, 0이 아닌 유저만 모아 streak snapshot을 만들고 rank를 저장했다. 조회 시점에는 이미 정렬이 끝난 결과에서 필요한 rank 범위만 읽으므로, 깊은 페이지에서도 비용이 흔들리지 않는다.

Solved: bucket 기반 rank 계산

solved count별 인원수와 상위 인원수를 별도 bucket 테이블에 저장했다. 이를 이용해 전체 순위를 tie group 내부 순위 문제로 축소했지만, 분포에 따라 tie group 내부 offset 비용이 다시 드러날 수 있다.

핵심 판단

current streak는 조회 전에 rank를 끝내 두는 방식, solved는 조회 시 rank 계산 범위를 줄이는 방식이다. 둘의 성능 차이는 바로 이 사전 계산 강도의 차이에서 나온다.

표 수치 차이가 수만 배라서 log scale dot plot으로 바꿨다. 오른쪽으로 갈수록 느리다.

Naive Optimized

snapshot을 읽는 구조로 바뀌자, 뒤쪽 페이지에서도 조회 시간이 거의 일정하게 유지됐다.

시각화: Solved 지연 시간

Solved는 bucket으로 범위를 줄였지만, 큰 tie group에서는 내부 offset 비용이 남는다. 그래프가 이 한계를 그대로 보여준다.

Naive Optimized

front 페이지에서는 bucket 계산 오버헤드가 약간 있지만, 중간 구간부터는 이득이 압도적이다. 다만 큰 tie group에서는 완전한 해결이 아니다.

한계와 다음 단계

현재 한계

solved는 전체 순위 문제를 tie group 내부 문제로 줄였지만, solved_count=1처럼 큰 group에서는 내부 offset이 다시 병목이 된다.

다음 개선 방향

tie group 내부도 seek 방식으로 읽거나, solved 조회 역시 snapshot 계열 구조로 전환하면 깊은 페이지 비용을 더 낮출 수 있다.
